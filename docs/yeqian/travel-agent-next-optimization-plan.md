# Travel Agent 下一阶段优化计划

## 结论

当前 Travel Agent 已完成从自然语言输入到结构化旅行计划展示的 MVP 闭环，但距离“真正听懂用户、生成可执行行程、支持自然多轮调整”仍有差距。下一阶段优化应优先解决输入信息不足、行程内容过粗、多轮补充无效、非流式返回和快捷提示不个性化等问题。

## 当前问题总览

| 优先级 | 问题 | 影响 | 建议方向 |
| --- | --- | --- | --- |
| P0 | 首次输入表单信息不足 | 后端缺少关键旅行条件，容易生成泛化计划或反复追问 | 完善首次输入表单，区分必填项和可选偏好 |
| P0 | Agent 对用户补充理解不足 | 用户说“没有详细计划”时，系统仍返回类似内容 | 增强多轮意图识别，区分细化、重写、调整、补充信息 |
| P0 | 生成行程不够详细 | 用户无法直接照着走，计划可执行性不足 | 改造行程生成规则，输出具体时间、地点、交通、餐饮、耗时 |
| P1 | 输出不是流式返回 | 生成内容较多时等待感强 | 增加 SSE 流式接口和前端逐段展示 |
| P1 | 快捷提示不个性化 | 提示与当前上下文无关，像固定模板 | 根据当前会话和行程状态生成上下文建议 |

## 1. 首次输入表单信息不足

### 现象

首次生成计划时，前端表单收集的信息不够完整，导致后端拿到的旅行需求缺少关键条件。

当前表单主要关注：

- 目的地。
- 天数。
- 旅行风格。
- 同行人。
- 补充说明。

但旅行规划实际还需要：

- 出发城市。
- 出发日期或时间范围。
- 总预算。
- 人数。
- 交通偏好。
- 酒店偏好。
- 是否带老人、孩子或宠物。
- 是否自驾。
- 必去景点。
- 想避开的内容。
- 餐饮偏好。
- 行程节奏。

### 影响

- 后端缺少必要字段后，只能猜测或触发追问。
- 首次生成结果容易泛化。
- 用户会觉得系统没有充分理解需求。

### 改造方向

- 首次输入表单增加必填项：
  - 出发城市。
  - 出发日期或时间文本。
  - 出行天数。
  - 目的地或目的地偏好。
- 首次输入表单增加可选偏好：
  - 总预算。
  - 人数。
  - 交通偏好。
  - 酒店偏好。
  - 餐饮偏好。
  - 行程节奏。
  - 必去景点。
  - 避免事项。
- 表单提交时生成更完整的自然语言 message，并传给后端。

### 验收标准

- 用户首次输入时可以明确填写出发地、目的地、日期、天数。
- 缺少必要字段时，前端能提前提示或后端能返回明确追问。
- 后端收到的 `message` 中包含核心旅行条件。

## 2. Agent 对用户补充理解不足

### 现象

用户后续输入“没有详细的旅游计划啊”时，系统仍然返回和上一轮类似的内容，没有理解用户是在要求“细化当前计划”。

### 影响

- 多轮对话像重复单轮生成。
- 用户反馈无法改变输出结果。
- Agent 缺少上下文感。

### 改造方向

- 增加多轮意图识别能力，至少识别以下意图：
  - `DETAIL_PLAN`：细化当前计划。
  - `REGENERATE_PLAN`：重新生成计划。
  - `ADJUST_PLAN`：调整已有计划。
  - `ADD_CONSTRAINT`：补充约束条件。
  - `ANSWER_CLARIFICATION`：回答系统追问。
- 保存上一轮 `recommendedPlan`，后续请求可基于已有计划增量调整。
- 用户表达“不详细”“太笼统”“没看懂”“重新安排”等反馈时，不应简单重复原计划。

### 验收标准

- 输入“没有详细的旅游计划啊”后，系统能返回更细的时间点、地点和安排。
- 输入“第二天轻松一点”后，只调整第二天或重点解释第二天变化。
- 输入“换一些餐厅”后，优先调整餐饮建议，而不是重写整个计划。

## 3. 生成行程不够详细

### 现象

当前计划虽然有 `上午 / 下午 / 晚上` 结构，但内容过于概括。

示例问题：

```text
上午：宝鸡核心景点游览
下午：预留返程交通和退房时间
晚上：返程或轻松收尾
```

这类内容无法直接指导用户出行。

### 目标效果

更理想的输出应包含具体地点、时间、交通、餐饮和注意事项。

示例：

```text
上午：
08:30 从酒店出发
09:00 到达法门寺文化景区
09:00-11:30 游览合十舍利塔、法门寺博物馆
11:30-12:30 在景区附近午餐

下午：
13:00 前往太白山游客中心
14:00-17:00 游览太白山低强度线路
17:30 返回市区

晚上：
18:30 陈仓老街晚餐
20:00 返回酒店休息
```

### 改造方向

- 改造 `ItineraryPlanner`，避免输出空泛描述。
- 每个时间段至少包含：
  - 时间范围。
  - 具体地点。
  - 活动内容。
  - 交通建议。
  - 预计耗时。
  - 必要注意事项。
- 对“核心景点游览”“自由活动”“轻松收尾”等泛化词做降级检查。
- 没有真实数据时，可以输出“需二次确认”的候选建议，但不能只写泛化模板。

### 验收标准

- 每天至少有 3 个以上具体活动项。
- 每个活动项包含具体地点或明确待确认地点。
- 行程中不应大量出现“核心景点游览”“自由活动”“轻松收尾”这类空泛表达。
- 宝鸡、杭州、上海、西安等常见目的地能生成可执行日程。

## 4. 输出不是流式返回

### 现象

当前接口需要等完整结果生成后一次性返回，用户等待期间只能看到加载状态。

### 影响

- 生成时间长时体验差。
- 用户不知道系统正在做什么。
- 旅行计划内容较多时缺少逐步反馈。

### 改造方向

- 后端新增 SSE 流式接口，例如：

```text
POST /api/travel/plans/stream
```

- 流式事件可以按阶段返回：
  - 正在理解旅行需求。
  - 正在检查缺失信息。
  - 正在查询天气和搜索结果。
  - 正在生成每日行程。
  - 正在整理提醒和风险。
  - 已完成结构化行程。
- 前端逐段展示 AgentTravel 回复，最终再渲染完整 `Itinerary`。

### 验收标准

- 前端能在完整行程生成前看到阶段性文本。
- 流式失败时能回退为普通错误提示。
- 非流式接口保持兼容。

## 5. 快捷提示不个性化

### 现象

当前对话框上方快捷提示是固定内容，例如：

```text
增加一天行程
换一些餐厅
太累了，减少些景点
```

这些提示不一定符合当前用户的真实需求和上下文。

### 影响

- 提示像模板按钮，不像智能建议。
- 用户不一定愿意点击。
- 对话体验不够个性化。

### 改造方向

- 根据当前响应状态生成快捷提示：
  - 如果 `needClarification=true`，提示用户补充缺失字段。
  - 如果行程过粗，提示“细化每天上午下午晚上安排”。
  - 如果有多城市跨城，提示“减少跨城交通”。
  - 如果预算缺失，提示“补充预算范围”。
  - 如果已有完整计划，提示“调整第 2 天”“换酒店区域”“增加亲子项目”等。
- 快捷提示应来自当前上下文，而不是固定数组。

### 验收标准

- 不同会话显示不同快捷提示。
- 缺失信息场景下，快捷提示能引导用户补充关键字段。
- 完整行程场景下，快捷提示能围绕当前目的地、天数和行程内容调整。

## 推荐实施顺序

### P0：先提升可用性

1. 完善首次输入表单。
2. 增加多轮意图识别。
3. 改造行程生成详细度。

### P1：再提升体验

1. 个性化快捷提示。
2. 前端行程展示细节优化。
3. SSE 流式输出。

### P2：后续增强

1. RAG 攻略知识库。
2. MCP 工具平台。
3. 真实票务下单。
4. 真实酒店预订。
5. 写入型前端能力。
