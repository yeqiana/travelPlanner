# Travel Agent 多轮局部调整规则

## 结论

继续优化多轮调整时，必须先保存上一轮完整计划上下文，再基于上下文做局部调整。否则“第二天轻松一点”“换一些餐厅”“酒店换商圈”“减少跨城交通”会退化成重新生成整份计划，容易丢失上一轮已确认内容。

## 上下文保存策略

- `travel_session.partial_intent_json` 继续保存上一轮完整旅行意图，用于多轮合并。
- `travel_session.last_response_json` 保存上一轮完整计划上下文，包含：
  - `planId`
  - `intent`
  - `recommendedPlan`
  - `reminders`
  - `risks`
- 完整计划落库并生成 `planId` 后，再更新 `last_response_json`，避免保存未落库版本。
- 追问态会话仍以 `partial_intent_json` 和 `last_questions_json` 为主；完成态会话可恢复上一轮计划用于细化和调整。

## 局部调整优先级

1. 餐饮关键词：`餐厅`、`吃`、`美食`、`餐饮`、`小吃`、`晚餐`、`午餐`。
2. 酒店关键词：`酒店`、`住宿`、`住哪里`、`住哪`、`民宿`、`商圈`。
3. 交通关键词：`交通`、`高铁`、`飞机`、`自驾`、`打车`、`地铁`、`跨城`、`换乘`。
4. 按天关键词：`第2天`、`第二天`、`第3日` 等。

命中明确维度时，只替换对应字段；未命中明确维度时，仅追加待办提示，避免误改整份计划。

## 局部调整边界

- 按天调整只修改目标 `DailyPlan`，其他天保持上一轮内容。
- 餐饮调整优先替换每天 `evening` 中的餐饮表达，并追加餐饮二次确认待办。
- 酒店调整只追加 `hotelSuggestions` 和待办，不改路线和日程。
- 交通调整只追加 `transportSuggestions` 和待办，不直接改路线顺序。
- 涉及真实票价、营业时间、房态、班次时必须写“需二次确认”，不输出确定性承诺。

## 后续可扩展项

- 增加结构化 `activities` 后，可把局部调整从文本替换升级为活动级替换。
- 接入真实 POI、酒店和交通数据后，可把候选替换从规则兜底升级为证据驱动。
- 引入调整 diff 字段后，前端可高亮“本轮改了哪里”。
