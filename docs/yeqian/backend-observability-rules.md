# 后端可观测性规则

## 结论

后端不能只返回最终结果。旅行规划链路较长，必须通过日志说明一次请求经历了哪些阶段、每个阶段产出了什么摘要、失败时卡在哪里。

## 适用范围

- 旅行计划生成接口。
- 多轮追问接口。
- 工具执行链路。
- 证据归一、候选方案、评分、行程、提醒、一图流生成链路。
- 旅行计划持久化和历史查询。

## 日志目标

一次用户输入进入后端后，应能通过同一个 `traceId` 串起以下信息：

- 请求入口：`sessionId`、用户输入摘要。
- 多轮意图识别：识别出的 `dialogIntent`。
- 旅行意图解析：出发地、日期、天数、人数、预算、目的地、风格。
- 缺失信息检查：是否需要追问、追问问题。
- 会话处理：是否保存追问会话、是否标记完成。
- 查询任务拆解：任务数量、任务类型、城市。
- 工具执行：使用的工具、任务类型、城市、成功或失败、耗时、错误摘要。
- 证据归一：证据数量、证据类型、城市、来源。
- 候选方案和评分：候选数量、最高分。
- 行程生成：标题、天数、风险数量、待办数量。
- 提醒和一图流：提醒数量、一图流标题。
- 持久化：`planId`、任务/证据/提醒写入数量。
- 请求出口：最终结果、耗时。

## 日志安全规则

- 不打印 API Key、Token、数据库密码等敏感信息。
- 用户输入只打印摘要，避免超长文本刷屏。
- 工具返回结果不直接打印完整 JSON，只打印成功状态、来源和错误摘要。
- 异常日志需要包含堆栈，普通阶段日志不打印完整对象。

## 开发环境日志格式

开发环境控制台日志需要包含 `traceId`：

```text
2026-05-07 10:00:00.000 INFO  [travel-xxxxxx] c.y.t... - 旅行计划请求开始...
```

如果日志显示 `no-trace`，说明该日志不是从旅行计划请求链路中触发，或当前线程没有设置 `MDC traceId`。

## 验收标准

- 调用 `POST /api/travel/plans` 后，控制台能看到同一个 `traceId` 下的完整阶段日志。
- 工具失败时，日志能看出失败的工具来源、任务类型、城市和错误原因。
- 需要追问时，日志能看出缺失字段和追问问题。
- 完整计划生成成功时，日志能看出最终 `planId` 和总耗时。
