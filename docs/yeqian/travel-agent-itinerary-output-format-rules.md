# Travel Agent 行程方案输出格式规则

## 结论

旅行方案输出应同时具备“策略解释”和“可执行清单”两层能力：先说明为什么这样安排，再给用户可以直接照着走的时间轴、预算、交通、餐饮和风险替代方案。

## 适用范围

- 用户要求生成多日旅行方案。
- 用户明确给出预算、出发地、目的地、人数、交通、住宿、餐饮、节奏或避坑偏好。
- 用户需要对不同 AI 方案进行比较后，沉淀为稳定的旅行规划输出模板。
- 后续新增或优化 `Travel Agent` 行程生成、详情展示、提示词模板和前端渲染时，应优先参考本文档。

## 总体结构

行程方案建议按以下顺序输出：

1. 一句话结论。
2. 关键策略。
3. 预算总览。
4. 交通与住宿建议。
5. 每日行程。
6. 餐饮建议。
7. 风险与替代方案。
8. 一页式清单。

## 一句话结论

开头必须先用一句话明确本次方案定位，避免直接堆景点。

示例：

```text
这是一套五一避峰、情侣慢游、预算 5000 元内的西安到杭州 3 天方案，主打西湖西线、茶园和城市烟火，不走高强度打卡路线。
```

要求：

- 说明目的地、天数、预算或核心约束。
- 说明旅行风格，例如放松、亲子、情侣、慢游、避峰、轻户外。
- 避免夸大确定性，例如“精准控预算”“绝对不排队”。

## 关键策略

在详细行程前，应先给出 2 到 4 条关键策略，帮助用户理解取舍。

示例：

```text
- 不住湖滨核心圈，优先住地铁方便但相对安静的区域。
- 不冲断桥、雷峰塔等高拥挤点，主走西湖西线、茶园和运河街区。
- 每天只安排 1 条主线，再给 1 个轻量备选，避免五一过度赶路。
```

要求：

- 策略必须能对应用户偏好，例如预算、节奏、交通、住宿、避坑。
- 对关键取舍要说明原因。
- 不要只写泛泛的“轻松游”“深度游”。

## 预算总览

预算应按模块拆分，并标注哪些信息需要实时核实。

建议拆分：

- 大交通。
- 住宿。
- 餐饮。
- 市内交通。
- 门票与体验。
- 机动预算。

要求：

- 高铁票价、酒店价格、门票政策、预约状态等实时信息，不得写成最终确定事实。
- 如果没有实时查询依据，应标注“需以 12306 / 酒店平台 / 官方预约页面为准”。
- 预算结论应使用“目标控制”“预计区间”“需二次确认”等表述，避免“精准控预算”。

示例：

```text
预算目标：2 人总预算控制在 5000 元左右。

- 高铁往返：约 2800 元，需以 12306 实时票价为准。
- 住宿 2 晚：约 800 到 1200 元，需以酒店平台五一房价为准。
- 餐饮：约 800 到 1000 元。
- 市内交通：约 200 到 300 元。
- 门票与体验：约 300 到 500 元。
```

## 交通与住宿建议

交通与住宿不要只给单点结论，应给出筛选逻辑和备选区域。

交通要求：

- 明确出发城市、到达城市、优先车站或车站选择理由。
- 涉及具体车次、时间、票价时，必须标注需实时核实。
- 返程日必须预留车站交通、安检、进站缓冲时间。

住宿要求：

- 优先给住宿区域和筛选标准，再给具体酒店示例。
- 不应只押注一家酒店。
- 地铁口、步行距离、装修年份、价格、房态、隔音等信息需要实时核实。

示例：

```text
住宿优先区域：

- 杭州东站 / 西湖文化广场：地铁方便，适合高铁往返和预算控制。
- 武林广场 / 凤起路：进西湖和城市商圈都方便，但五一价格可能更高。
- 滨江：更安静，酒店性价比可能更好，但去西湖西线时间更长。
```

## 每日行程

每日行程应按时间段组织，但不要把不确定信息写死。

推荐结构：

```text
Day 1：抵达适应 + 轻量散步

下午：
- 抵达杭州后前往酒店，办理入住并休整。
- 如果体力允许，前往杨公堤 / 茅家埠散步，作为低强度适应。

晚上：
- 可选南宋御街或河坊街简单吃小吃。
- 如果人流过大，直接在酒店附近吃饭并休息。

缓冲提醒：
- 抵达日不安排跨城区密集景点。
- 晚间活动作为选做，不影响第二天主线。
```

要求：

- 每天必须有主线主题，例如“西湖西线慢游”“茶园九溪轻徒步”“运河街区返程日”。
- 每天至少给出上午、下午、晚上或抵达、白天、返程三个时段。
- 每天应包含主推荐和备选方案。
- 每天应给出交通缓冲或体力缓冲提醒。
- 返程日前不建议安排跨城区高风险行程。

## 餐饮建议

餐饮建议应按场景组织，而不是只列网红店。

推荐拆分：

- 早餐。
- 小吃。
- 正餐。
- 下午茶或轻体验。
- 避坑提醒。

要求：

- 优先匹配用户餐饮偏好，例如当地小吃、清淡、预算友好、情侣氛围。
- 店名、营业时间、排队情况、地址必须标注需实时核实。
- 不要把游客街主街小吃包装成“本地人私藏”。

## 风险与替代方案

节假日、热门城市、亲子或情侣慢游方案必须提供风险替代。

至少覆盖：

- 人太多怎么办。
- 下雨怎么办。
- 预约失败怎么办。
- 太累怎么办。
- 预算超了怎么办。

示例：

```text
- 如果灵隐预约失败：改为法喜寺周边轻逛，或直接切换到小河直街 / 运河散步。
- 如果九溪下雨不适合走路：改为中国茶叶博物馆、咖啡店和商圈慢逛。
- 如果返程日体力不足：取消跨城区景点，只保留酒店附近午餐和提前进站。
```

## 一页式清单

最后应给用户一个可截图保存的执行清单。

建议包含：

- 每天主线。
- 必须提前确认的信息。
- 预算提醒。
- 交通缓冲。
- 预约入口提示。
- 可取消的低优先级活动。

示例：

```text
一页式清单：

- Day 1：抵达杭州 -> 酒店休整 -> 杨公堤 / 茅家埠 -> 早休息。
- Day 2：龙井村 -> 九溪 -> 西湖西线夜景，体力不足则取消夜间活动。
- Day 3：灵隐或小河直街二选一 -> 提前 60 到 90 分钟到车站。
- 出发前确认：12306 车票、酒店房价、景区预约、天气、返程车站交通。
```

## 禁止事项

- 不要把未经实时核实的车次、票价、酒店价格、预约状态写成确定事实。
- 不要把“地铁直达”写给实际需要换乘公交、打车或步行较远的景点。
- 不要在返程日前安排多个跨城区景点。
- 不要只给一个酒店或一个餐厅作为唯一选择。
- 不要使用“绝对不排队”“精准预算”“本地人私藏”等无法验证或过度营销的表达。
- 不要只列景点，不解释为什么符合用户偏好。

## 质量自检

生成行程方案后，应检查：

- 是否先给结论，再解释策略。
- 是否区分了确定信息和需实时核实信息。
- 是否符合用户预算、人数、交通、住宿、餐饮、节奏和避免事项。
- 是否给了返程日缓冲。
- 是否给了人流、天气、预约失败和体力不足的替代方案。
- 是否保留一页式清单，方便用户直接执行。
