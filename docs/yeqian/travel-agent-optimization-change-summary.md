# Travel Agent 下一阶段优化改动对比说明

## 本次追加更新：上一轮完整计划上下文与局部调整

- 已新增 `travel_session.last_response_json` 保存策略，用于保存上一轮完成态计划上下文。
- 已新增 `PreviousTravelPlanContext`，保存 `planId`、`intent`、`recommendedPlan`、`reminders`、`risks`。
- 已在完整计划落库后回写完成态会话上下文，后续多轮调整可以读取上一轮完整推荐计划。
- 已新增规则型局部调整器，支持按天、餐饮、酒店、交通四类优先局部调整。
- 已新增 `docs/yeqian/travel-agent-local-adjustment-rules.md` 和 `docs/yeqian/phase8_previous_plan_context_migration.sql`。

## 结论

本轮改动已经完成 `travel-agent-next-optimization-plan.md` 中的主要 P0 能力，并补上部分 P1 能力：首次输入信息更完整、多轮反馈可识别、完成态会话可继续细化、行程内容更具体、快捷提示可按上下文生成，并新增了基础 SSE 流式接口。

仍未完成的是更深层的真实数据能力、生产级流式前端体验、复杂局部编辑、RAG / MCP / 真实下单等后续增强项。

## 修改前后区别

| 模块 | 修改前 | 修改后 |
| --- | --- | --- |
| 首次输入表单 | 主要填写目的地、天数、风格、同行人、补充说明。缺少出发地、日期、预算、交通、酒店、餐饮等关键条件。 | 新增出发城市、出发时间、人数、预算、交通偏好、酒店偏好、餐饮偏好、行程节奏、必去景点、避开事项等字段。 |
| 前端请求消息 | 表单会拼成较短的自然语言，如“我想去杭州玩3天”。 | 请求会拼成更完整的自然语言，包含“从哪里出发、什么时候出发、去哪里、玩几天、人数、预算、偏好”等核心条件。 |
| 缺失信息检查 | 必填检查主要覆盖出发地、日期、天数。目的地缺失时可能继续往后走。 | 增加目的地必填检查，缺失时返回结构化追问。 |
| 多轮意图识别 | 后续输入主要按普通新请求解析，用户说“不详细”“第二天轻松一点”时容易重新生成或重复原计划。 | 新增 `TravelDialogIntent` 和规则识别器，支持 `DETAIL_PLAN`、`REGENERATE_PLAN`、`ADJUST_PLAN`、`ADD_CONSTRAINT`、`ANSWER_CLARIFICATION`。 |
| 完成态会话 | `COMPLETED` 会话不参与恢复，后续调整缺少上一轮上下文。 | 完成态会话可恢复，后续细化和调整可以复用上一轮 `TravelIntent`。 |
| 局部调整理解 | “第二天轻松一点”里的“第二天”可能被误解析为总天数 2。 | 对 `ADJUST_PLAN` 做了规整，避免“第 N 天”误覆盖总天数。 |
| 行程详细度 | 每天主要是上午/下午/晚上概括文本，可能出现“核心景点游览”“轻松收尾”等空泛表达。 | 每段行程增加时间、地点、活动、交通/耗时、二次确认提示；先覆盖宝鸡、杭州、上海、西安的轻量地点兜底。 |
| 快捷提示 | 前端固定展示“增加一天行程”“换一些餐厅”“太累了，减少些景点”。 | 后端新增 `contextualSuggestions`，前端优先展示上下文提示；为空时保留固定兜底。 |
| 响应契约 | `TravelPlanResponse` 没有明确返回本轮多轮意图和上下文提示。 | 增量新增 `dialogIntent`、`contextualSuggestions`，旧字段不删除。 |
| SSE 流式接口 | `POST /api/travel/plans/stream` 文档标记未实现。 | 新增基础 SSE 接口，返回 `stage`、`completed`、`error` 事件。 |
| 前端流式能力 | 没有流式 provider。 | 新增 `streamTravelPlanningProvider.ts`，可消费 SSE 最终结果；当前主流程仍可继续使用非流式接口。 |
| 文档 | 只有下一阶段优化计划和接口旧说明。 | 新增多轮意图、详细行程、上下文快捷提示、SSE 契约等规则文档，并更新接口文档。 |
| 测试 | 主要覆盖原 MVP 链路。 | 新增/增强多轮意图、上下文提示、详细行程、完成态会话恢复、SSE 控制器测试。 |

## 尚未完成

- 已完成浏览器手工验收：新增表单字段、小屏滚动、快捷提示、追问和完整计划展示已做基础检查。
- 已将 SSE provider 接入聊天页，阶段文本可替代纯 loading 动画；非流式接口仍作为失败兜底。
- SSE 当前是基础阶段事件，不是模型 token 级实时输出，也没有取消、重试、断线恢复能力。
- 多轮调整仍是规则级局部改写，已支持按天、餐饮、酒店、交通四类基础调整；尚未支持结构化活动级 diff 和前端高亮差异。
- 完成态会话已保存上一轮 `recommendedPlan` 完整结构用于局部改写；生产环境需执行 `docs/yeqian/phase8_previous_plan_context_migration.sql`。
- 行程详细地点只做了宝鸡、杭州、上海、西安的轻量兜底，其他城市仍使用候选地点和二次确认表达。
- 交通、酒店、餐饮仍以规则和 mock/降级为主，没有真实库存、价格、余票、预约名额保证。
- 没有引入 RAG 攻略知识库。
- 没有引入 MCP 工具平台。
- 没有实现真实票务下单、酒店预订、支付或订单能力。
- 没有做性能、并发、多实例 session 一致性和生产监控告警验证。
- 已创建数据库迁移保存上一轮完整计划上下文；尚未做线上迁移执行和回滚验证。

## 后续建议

1. 先做前端浏览器手工验收，重点看新增表单是否拥挤、移动端是否溢出、追问和完整计划是否能正常展示。
2. 再把 SSE provider 接入聊天页，用阶段文本替代纯 loading 动画。
3. 下一步优化多轮调整时，建议增加结构化 `activities` 和调整 diff 字段，让前端可高亮展示“本轮改了哪里”。
4. 如果要提升行程真实性，应优先补酒店、餐饮、景点开放预约和城市 POI 数据来源，而不是继续堆规则模板。
