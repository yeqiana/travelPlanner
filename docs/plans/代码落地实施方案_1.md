## 2. 项目目标理解

本项目第一版目标是实现旅游规划 Agent MVP 最小闭环。

技术边界：

- 使用 Spring Boot 3.x
- 使用 Spring AI Alibaba
- 大模型优先接 DashScope / 通义千问
- 配置层预留模型提供商切换能力：DashScope / 通义千问、豆包、OpenAI
- 使用 Tool Calling
- 不做复杂 RAG
- 不做 MCP
- 不直接买票
- 不直接订酒店
- 不做前端
- 先跑通后端最小闭环

最小闭环链路：

```text
用户输入
→ 需求解析
→ 缺失信息判断
→ 查询任务拆解
→ 工具调用
→ 证据归一化
→ 候选方案生成
→ 方案评分
→ 行程生成
→ 提醒生成
→ 一图流文案生成
→ 返回用户
```

### 4.3 Application 层


职责：

- 作为接口入口的应用服务
- 调用 Agent 编排器
- 不承载复杂业务逻辑

### 4.4 Agent 编排层

```text
TravelAgentOrchestrator
```

职责：

- 串联最小闭环流程
- 控制步骤顺序
- 处理降级和兜底

第一阶段编排链路：

```text
TravelIntentParser
→ MissingInfoChecker
→ TravelTaskPlanner
→ ToolExecutor
→ EvidenceNormalizer
→ CandidatePlanGenerator
→ TravelScorer
→ ItineraryPlanner
→ ReminderGenerator
→ ImageBriefGenerator
```

### 4.5 AI 解析类

```text
TravelIntentParser
```

职责：

- 调用真实 AI
- 将用户输入解析为 `TravelIntent`
- 约束模型输出 JSON
- 解析失败时返回可控错误

### 4.6 规则检查类

```text
MissingInfoChecker
```

职责：

- 检查是否缺少出发地、时间、天数
- 人数、预算、偏好可默认
- 只在必要时追问

### 4.7 任务规划类

```text
TravelTaskPlanner
```

职责：

- 根据 `TravelIntent` 生成查询任务
- 第一阶段可先用规则生成，不强依赖 AI

### 4.8 工具执行类

```text
ToolExecutor
WebSearchTool
WeatherTool
AttractionInfoTool
TransportSearchTool
HotelSearchTool
MapRouteTool
```

职责：

- `ToolExecutor` 根据任务类型分发工具
- 工具类保留 Spring AI `@Tool` 接入形式
- 第一阶段大部分工具先 mock

### 4.9 证据归一化类

```text
EvidenceNormalizer
```

职责：

- 把工具结果统一转成 `TravelEvidence`
- 标记来源、置信度、抓取时间
- 工具失败时保留失败信息并允许流程继续

### 4.10 方案生成与评分类

```text
CandidatePlanGenerator
TravelScorer
ItineraryPlanner
ReminderGenerator
ImageBriefGenerator
```

职责：

- 候选方案生成：第一阶段 mock / 规则
- 评分：第一阶段规则评分
- 行程生成：可调用真实 AI
- 提醒生成：规则生成
- 一图流文案：可调用真实 AI 或先规则生成

## 6. 哪些模块先做 mock

第一阶段建议 mock：

```text
WebSearchTool
WeatherTool
AttractionInfoTool
TransportSearchTool
HotelSearchTool
MapRouteTool
CandidatePlanGenerator
TravelScorer
ReminderGenerator
```

原因：

- 外部搜索、天气、地图、酒店、交通 API 接入成本高
- 第一阶段重点是验证 Agent 编排链路
- mock 可以保证最小闭环稳定可测
- 不影响后续替换为真实工具

mock 数据要求：

- 必须结构化
- 必须带 source
- 必须带 fetchedAt
- 必须能覆盖天气、交通、酒店、景点、路线风险
- 必须显式标记“需二次确认”的内容

## 7. 哪些模块调用真实 AI

第一阶段建议真实调用 AI：

```text
TravelIntentParser
ItineraryPlanner
```

可选真实调用 AI：

```text
ImageBriefGenerator
```

不建议第一阶段真实调用 AI：

```text
TravelScorer
MissingInfoChecker
ToolExecutor
```

原因：

- `TravelIntentParser` 是最关键的自然语言入口，必须尽早验证模型解析能力
- `ItineraryPlanner` 是最终用户感知最强的输出，适合真实 AI 生成
- 缺失信息检查和评分更适合规则，稳定、可测、可解释
- 工具执行第一阶段先 mock，避免外部 API 干扰闭环验收

## 10. 第一阶段接口范围

第一阶段只提供一个核心接口：

```http
POST /api/travel/plans
```

请求：

```json
{
  "message": "五一从西安出发，4天，两个人，预算3000，想去杭州上海周边，不想太累",
  "sessionId": "optional-session-id"
}
```

响应需要包含：

```json
{
  "needClarification": false,
  "clarificationQuestions": [],
  "intent": {},
  "tasks": [],
  "evidences": [],
  "candidatePlans": [],
  "recommendedPlan": {},
  "score": {},
  "reminders": [],
  "imageBrief": {}
}
```

缺失信息时响应：

```json
{
  "needClarification": true,
  "clarificationQuestions": [
    "你是从哪个城市出发？",
    "计划出行几天？"
  ]
}
```

## 11. 第一阶段验收方式

### 11.1 启动验收

执行：

```bash
mvn spring-boot:run
```

验收标准：

```text
应用可以正常启动
无 Bean 注入失败
无配置绑定失败
```

### 11.2 AI 调用验收

输入：

```text
五一从西安出发，4天，两个人，预算3000，想去杭州上海周边，不想太累
```

验收标准：

```text
TravelIntentParser 能真实调用 DashScope / 通义千问
能解析出 departureCity = 西安
能解析出 dateText = 五一
能解析出 days = 4
能解析出 peopleCount = 2
能解析出 budget = 3000
能解析出 destinationPreferences 包含杭州、上海周边
能解析出 travelStyles 包含不想太累
```

### 11.3 缺失信息验收

输入：

```text
五一想出去玩，不想太累
```

验收标准：

```text
needClarification = true
clarificationQuestions 至少包含出发地、出行天数相关问题
不强制追问预算
不强制追问人数
```

### 11.4 最小闭环验收

输入：

```text
五一从西安出发，4天，两个人，预算3000，想去杭州上海周边，不想太累
```

验收标准：

```text
接口返回 HTTP 200
needClarification = false
返回 intent
返回 tasks
返回 mock evidences
返回候选方案
返回评分
返回推荐行程
返回提醒事项
返回一图流文案结构
```

### 11.5 边界验收

必须满足：

```text
不直接买票
不直接订酒店
不承诺实时余票准确
无证据内容标记“需二次确认”
不引入 RAG
不引入 MCP
不实现前端
```
